# Armin Phase 2.5 UX Design

Armin 不解决“Agent 能不能工作”的问题。

Armin 关注的是：当 Agent 能持续工作之后，人应该如何管理这些工作。

当前核心问题不是代码生成能力，而是：

- Agent Management Cost
- Attention Management
- Task-centric Coordination
- Asynchronous Human-Agent Collaboration

Phase 2.5 不是大重构。它的目标是在尽量少改动现有能力的前提下，让 UI/UX 从：

```text
Remote Agent Controller
```

逐步转向：

```text
Task-centric Agent Workspace
```

用户打开 App 第一眼应该看到：

- 哪些任务正在推进
- 哪些任务需要我处理
- 哪些任务已经完成
- 自上次查看后发生了什么
- 我现在应该做什么决策

而不是：

- 哪个 Agent session 在跑
- 哪个 tmux session 在跑
- 哪个 host 在执行
- 哪个日志需要查看
- 哪个技术状态需要排障

## 1. 产品论纲：2026 修订版

Armin 的新定位不是：

- 聊天工具
- 远程桌面
- 移动 IDE
- AI 操作系统
- 飞书/Slack 替代品
- Codex Mobile 复刻
- Litter 复刻

Armin 的定位是：

> 以任务为中心的 Agent 异步协调层

也就是：

> 以任务为中心的 Agent 异步协作层。

Agent、CLI、tmux、host、session 都是实现细节。它们让任务能够真实运行，但不应该成为用户心智中的一等公民。

Task 才是一等公民。用户不是来管理终端窗口、Agent session 或 SSH 连接的；用户是来委派、推进、确认、暂停、恢复和验收工作的。

Phase 2 已经证明 Armin 可以通过真实 SSH/tmux、Codex/Qoder、语音/文本追加、任务详情页和审计链路跑通真实执行。Phase 2.5 要验证的是：这些能力能否被组织成一个更轻的任务工作区，而不是一个远程运行时控制台。

## 2. From Static Task to Living Task

Armin 中的 Task 不应该只是 Todoist 或 Jira 那样的静态任务。

Armin 的 Task 应该是：

> Living Task

Living Task 是一个会持续推进、持续产出、持续请求决策的工作实体。它不是一条待办，也不是一个聊天线程，也不是一个裸露的 Agent session。

Living Task 应该包含：

- 目标：用户希望完成什么
- 当前状态：工作现在处于什么阶段
- 最新进展：自上次查看后发生了什么
- 下一步动作：任务是否需要用户处理
- 结果/交付物：当前可验收的输出是什么
- 上下文追加：用户可以继续补充约束或信息
- 审计历史：任务如何被创建、推进、暂停、恢复和验收

| 产品 | 一等公民 |
| --- | --- |
| Slack | 对话 |
| 飞书 | 工作区对话/业务对象 |
| Jira | Issue |
| Linear | Issue |
| Todoist | 静态任务 |
| Codex Mobile | Agent 会话 |
| Litter | Agent 会话 |
| Armin Phase 2 | 包裹在 Agent 会话周围的任务 |
| Armin Phase 2.5 目标 | Living Task |

Phase 2.5 的关键不是把 Task 做成项目管理对象，而是把它从“Agent session 的包装层”提升为“用户持续协作的工作实体”。

## 3. Agent 管理成本

传统开发中，用户主要是在执行工作：

```text
编写代码
```

Agent 工作流中，用户开始变成 Agent 的管理者：

```text
查看状态
追加指令
审批
恢复
停止
继续
验证结果
```

这意味着 Agent 并不只是在降低执行成本，也可能新增管理成本。用户不再只写代码，还要判断 Agent 在做什么、是否卡住、是否需要更多上下文、是否应该批准、结果是否可靠、什么时候该停止。

Armin 要验证的问题不是“用户是否喜欢语音”，而是：

> Agent 是否正在增加管理成本？

Phase 2.5 UX 应该降低这些管理成本：

- 查看状态成本：用户不应打开多个 tab 才知道任务现在怎样。
- 追加指令成本：用户应能快速补一句上下文，而不是进入控制台式流程。
- 审批成本：任务需要用户判断时，应直接说明决策内容和风险。
- 结果验收成本：任务应清楚呈现可验收结果、验证情况和剩余风险。
- 多任务切换成本：用户应知道哪些任务最需要注意，而不是逐个点开看。
- 错误恢复成本：恢复、重连、停止等动作应被解释为任务动作，而不是 runtime 排障。
- 上下文恢复成本：用户离开后回来，应先看到“发生了什么”和“现在需要什么”。

如果 Armin 无法降低这些成本，它就会继续像远程控制器；如果能降低这些成本，它才开始像 Agent 工作区。

## 4. 注意力管理

Agent 越强，用户越可能同时启动更多任务。

此时稀缺资源不是 Agent，而是人的注意力。

如果 UI 要求用户不断主动打开任务、查看日志、理解状态、判断是否卡住，就会加重注意力负担。用户会从"把任务委派出去"退回到"盯着 Agent 跑"。

Phase 2.5 UX 应该支持：

- 减少主动查看
- 突出需要用户处理的任务
- 把“下一步动作”显性化
- 将日志和调试信息降级为二级入口
- 用任务状态叙事替代运行时状态暴露

核心原则：

> 用户不应该监控 Agent。
> 用户应该在工作需要他们时响应工作。

这要求首页不再只是"当前任务 + 最近任务 + 大麦克风"，而应该像一个任务收件箱：把注意力先分配给需要处理的工作，再展示正在推进和最近完成的工作。

## 5. Talk to the Task

“给任务打电话 / Talk to the Task”是长期产品隐喻，不是当前已实现能力。

当前 Phase 2.5 不实现完整 Task Call，也不承诺实时语音电话、复杂路由或多 Agent runtime。

但 UI/UX 应该朝这个方向靠近：

- 用户不是找 Agent，而是找某件事。
- 每个任务拥有自己的上下文、历史、状态和审计链路。
- 用户在任何任务上下文中都能追加一句话。
- 语音只是追加上下文的一种方式。
- 系统未来可以决定调用哪个 Agent/session，但当前不实现复杂路由。

Phase 2.5 的目标不是“聊天入口更明显”。

而是：

> 让用户感觉自己在和任务协作，而不是在操作 Agent session。

因此，追加上下文不应该被设计成独立聊天页面。它应该是任务上下文中的自然动作：补充约束、回答问题、确认方案、要求继续、暂停、恢复或验收。

## 6. 更新后的心智模型

Phase 2 当前更接近这个模型：

```text
选择远程环境
-> 向 Agent 会话发送提示
-> 观察会话
-> 控制会话
-> 读取输出
```

它的问题是：用户被迫以运维者的视角理解 Agent 会话。

Phase 2.5 应转向这个模型：

```text
创建任务
-> 让它持续运行
-> 当它有进展、有问题或有结果时返回
-> 添加上下文或做出决策
-> 接受、继续、暂停或停止
```

压缩为一句话：

旧模型：

> 操作 Agent。

新模型：

> 管理工作。

这个心智转变决定了信息架构优先级：任务状态、进展、下一步和验收应高于 host、tmux、raw log、metrics 和 session cleanup。

## 7. Phase 2.5 信息架构

### 首页作为任务收件箱

Phase 2.5 首页应更接近：

```text
任务收件箱
├─ 需要处理
├─ 进行中
├─ 最近完成
└─ 草稿/创建任务
```

首页职责应从“启动语音/打开当前任务”转成“分配用户注意力”。

一级展示：

- 需要处理的任务数量
- 正在推进的任务数量
- 最近完成的任务数量
- 最重要的下一步动作
- 每个任务的人类可读状态
- 每个任务的最新进展摘要

降级展示：

- Agent command
- host
- project path
- tmux session
- raw runtime state

### 任务详情作为进展 + 决策界面

Phase 2.5 任务详情页应更接近：

```text
任务详情
├─ 任务状态摘要
├─ 自上次查看后的变化
├─ 下一步动作
├─ 活动时间线
├─ 结果/交付物
├─ 追加上下文
└─ 调试/运行时详情
```

一级展示：

- 任务标题
- 人类可读状态
- 最新进展
- 下一步动作
- 追加上下文入口
- 接受/继续/暂停/停止

二级展示：

- tmux
- SSH
- 主机
- 原始日志
- 指标
- 运行时丢失
- 重连
- 清理会话
- 提示预览

二级展示不是删除。它们仍然对真实执行、排障和高级用户有价值。但它们不应该主导第一屏，也不应该和用户决策动作同级竞争。

## 8. Phase 2.5 首页设计方向

首页设计目标：

用户一打开 App 就知道：

- 有多少任务在进行
- 有多少任务需要处理
- 哪些任务完成了
- 当前最重要的下一步是什么

首页第一印象不应该是：

- 大麦克风
- Agent Shell
- 远程控制器

首页文案可以从：

```text
AI coding agent Shell
```

调整为类似：

```text
你离开后，工作仍在继续推进。
```

或：

```text
你的 AI Agent 任务收件箱。
```

这只是设计建议，不要求在本文档中直接修改代码。

首页任务卡片应优先回答：

- 这件事现在处于什么状态？
- 自我上次看之后发生了什么？
- 它是否需要我做决定？
- 如果需要，我下一步该点哪里？

首页上的创建入口仍然重要，但它不应该压过任务收件箱。语音入口可以保留，但应从"产品中心"降级为"快速创建/快速追加的一种输入方式"。

## 9. Phase 2.5 任务详情设计方向

当前任务详情页同时承担：

- 用户协作界面
- 运行时控制台
- 调试日志页

Phase 2.5 应该把任务详情页改造成：

> 任务进展 + 决策界面

重点展示：

- 当前任务到底在做什么
- 最近发生了什么
- 是否需要我决策
- 我可以追加什么
- 我是否接受结果

建议一级结构：

```text
任务详情
├─ 状态摘要
│  ├─ 人类可读状态
│  ├─ 最新进展
│  └─ 时间/新鲜度
├─ 下一步动作
│  ├─ 批准/拒绝
│  ├─ 继续
│  ├─ 追加上下文
│  └─ 接受结果
├─ 结果/交付物
├─ 活动时间线
└─ 调试/高级
```

应降级到 调试/高级 区域：

- 日志
- 指标
- tmux 命令
- 清理会话
- 重连
- 运行时丢失
- 原始审批记录
- 终端选项内部细节

这不是否定这些能力。Phase 2 的真实执行链路仍然依赖 SSH/tmux、会话、日志和重连。但 Phase 2.5 的 UX 应把这些能力包在任务叙事之后，而不是让用户先成为运行时运维者。

## 10. 全局追加上下文入口

聊天不应该是独立页面。

追加上下文应该是全局能力。

用户在任何地方都应该能：

- 按住说话
- 输入一句补充
- 对当前任务或选定任务追加上下文

Phase 2.5 可以先设计，不一定立刻实现完整全局入口。关键是心智方向：用户不是进入一个聊天房间，而是在任务上下文里补充工作条件。

语音不是产品核心，而是降低任务协作摩擦的输入方式。

文本、语音、审批按钮、继续按钮本质上都应该服务同一件事：

> 帮用户围绕某个任务追加上下文或做出决策。

因此，语音入口需要和任务绑定，而不是作为独立品类信号存在。用户应该理解为“我在对这个任务说一句话”，而不是“我在打开一个语音助手”。

## 11. UX 原则

1. 任务优先，Agent 隐藏。
2. 展示工作进展，而非运行时机制。
3. 让下一步动作显而易见。
4. 减少主动查看状态。
5. 让用户响应，而非监控。
6. 语音是输入方式，不是产品品类。
7. 调试详情可用，但不主导。
8. 每个任务都应回答：发生了什么、下一步是什么、需要我做什么？
9. 优先使用人类任务状态，而非技术运行时状态。
10. 将接受、继续、暂停、停止与调试控件区分开。
11. 首屏优先展示任务叙事，而非原始日志。
12. 为离开电脑后又回来的用户优化体验。

## 12. UI 重构 MVP 范围

### 必须有

最小但高价值的改动：

- 首页从语音中心改成任务收件箱。
- 任务卡片按需要处理/进行中/已完成分区。
- 任务详情增加任务状态摘要。
- 追加指令入口更明显。
- 调试信息降级。
- 首页文案弱化 Agent Shell，强化任务持续推进。
- 任务卡片优先展示人类可读状态和最新进展，而不是执行环境。

### 应该有

有价值的第二层：

- 自上次查看后的变化摘要。
- 下一步动作卡片。
- 结果验收卡片。
- 更清晰的人类可读状态。
- 任务详情中将"结果/交付物"和"日志/调试"分离。
- 在需要审批、等待继续、运行丢失等状态下给出明确用户动作。

### 后续

明确不属于 Phase 2.5 核心范围：

- 完整给任务打电话功能。
- 多 Agent 路由。
- 长期任务记忆。
- 主动通知。
- 任务级语音通话。
- 跨任务智能调度。

Phase 2.5 不应变成一次过大的重构。它应该先验证：把现有能力重新组织成任务收件箱和任务决策界面后，用户是否更容易理解和使用 Armin。

## 13. Non-goals

Phase 2.5 不做：

- 完整多 Agent runtime
- 自动任务拆分
- 自动路由 Agent
- 完整语音电话体验
- 替代飞书/Slack
- 替代 IDE
- 完整项目管理系统
- 自动 commit/merge
- 大规模后端重构
- AI OS
- 通用终端模拟器
- 自动 fork/join runtime

这些方向可能在更远期被重新讨论，但不属于 Phase 2.5 的 UX 目标。

## 14. 待验证问题

后续需要验证的问题：

- 用户是否真的同时运行多个 Agent 任务？
- 用户是否会离开电脑后回来查看？
- 用户最常用操作是查看状态、追加指令、审批，还是验收？
- 用户是否更理解任务收件箱，而不是 Agent 会话？
- 用户是否觉得 Armin 减少了同步协作负担？
- 用户是否在公共场合使用语音？
- 用户是否会创建第二个任务，还是只把 Armin 当作单任务远程控制器？
- 用户是否能理解"等待继续"和"已完成"的区别？
- 用户是否需要调试入口，还是只在失败时需要？
- 用户是否愿意把验收动作交给手机端完成？

## 结语

Phase 2.5 的核心不是增加更多 Agent 能力，而是降低人管理 Agent 工作的成本。

Armin 当前已经具备真实执行、语音/文本追加、暂停/恢复、停止、确认完成、结果播报和任务详情审计。下一步 UX 的重点应是重新组织这些能力，让用户首先看见任务、进展、下一步和验收，而不是会话、主机、tmux 和日志。

一句话：

> Armin 应该让用户感觉自己在管理工作，而不是在操作 Agent。
