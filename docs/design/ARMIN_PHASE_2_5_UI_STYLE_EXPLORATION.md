# Armin Phase 2.5 UI Style Exploration

本文档用于 Phase 2.5 的轻量视觉探索。它不是完整 Design System，不设计复杂 token 系统，也不要求立即重构 Flutter theme。目标是找到适合 Armin 当前阶段的视觉方向。

## 1. 视觉设计目标

Phase 2.5 的视觉目标：

- 让 Armin 看起来像任务工作区，而不是聊天工具。
- 让用户感受到工作在持续推进。
- 降低技术控制台感。
- 提升信任感和可读性。
- 保留开发者工具的专业感。
- 不要过度娱乐化。
- 不要过度企业办公化。

视觉语言应服务于一个核心感受：我把工作放在这里，它会继续推进；当它需要我时，我能马上知道并回应。

## 2. 可能的视觉方向

### 方向 A：Linear 风格聚焦工作区

关键词：

- 简洁
- 聚焦
- 状态驱动
- 低噪音
- issue/工作项感

适合：

- 开发者
- Agent 编码工作流
- 任务优先产品定位

优点：

- 信息优先级清楚。
- 状态和下一步动作容易突出。
- 能自然支持 Needs Attention / In Progress / Completed 分区。
- 专业感足够，不会像聊天玩具。

风险：

- 可能太像项目管理工具。
- 情绪感不够。
- 如果表达过冷，用户可能感受不到“工作正在推进”。

### 方向 B：Notion/Arc 风格宁静工作区

关键词：

- 宁静
- 极简
- 柔和界面
- 可读
- 个人工作区

适合：

- 个人开发者
- 长时间使用
- 轻量异步协作

优点：

- 压力低，适合手机上反复查看。
- 有个人工作区感，不像企业后台。
- 能弱化运行时控制台气质。

风险：

- 可能不够体现 Agent 正在执行。
- 状态紧急度可能不够明确。
- 多任务并行时可能显得信号密度不足。

### 方向 C：指挥中心

关键词：

- 运维感
- 仪表盘
- 状态面板
- 执行监控
- 高信号密度

适合：

- 多任务并行
- 重度用户
- 高频 Agent 用户

优点：

- 状态密度高。
- 适合监控多个长任务。
- 对开发者排障友好。

风险：

- 容易回到 Remote Agent Controller 心智。
- 可能增加压迫感。
- 用户会被鼓励“监控 Agent”，而不是“响应工作”。

### 方向 D：友好 AI 同事收件箱

关键词：

- 亲切
- 温暖
- 收件箱
- 人类可读状态
- 助手感但不以聊天为先

适合：

- 降低新用户门槛
- 强调 Needs Attention
- 强调任务主动找人

优点：

- 容易表达“工作需要你回应”。
- 人类可读状态更自然。
- 空态和首次使用更友好。

风险：

- 可能显得不够专业。
- 可能和普通 AI assistant 混淆。
- 如果过暖，开发者会怀疑它是否足够可靠。

## 3. 推荐方向

推荐方向：

```text
Linear-like Focused Workspace
+
Friendly AI Coworker Inbox
```

具体含义：

- 信息结构像 Linear / Todoist。
- 状态表达像人类同事。
- 交互入口像任务收件箱。
- 视觉保持轻量、专业、可信。

为什么适合当前阶段：

- Armin 需要从 Agent session 心智转向 task inbox 心智。
- 当前用户大概率是开发者，需要专业、低噪、可扫读。
- Needs Attention 是 Phase 2.5 的核心，需要 inbox 风格承载。
- Friendly 的部分只用于状态语言和空态，不应把产品变成聊天助手。

为什么不建议纯 ChatGPT 风：

- 会强化 Chat First。
- 容易让用户以为 Armin 是一个通用聊天机器人。
- 不利于多任务分区和验收动作。

为什么不建议纯飞书风：

- 会强化人与人 IM / 协同办公心智。
- Armin 不是团队沟通工具。
- 容易让任务被对话流淹没。

为什么不建议纯终端风：

- 会回到 Remote Agent Controller。
- 会放大 SSH/tmux/logs 等实现细节。
- 不利于降低认知负担。

为什么不建议纯 Dashboard 风：

- 容易鼓励用户监控 Agent。
- 移动端会显得沉重。
- “下一步动作”可能被指标和状态卡淹没。

## 4. 色彩与氛围探索

不需要完整配色系统，但应明确状态气质。

### 背景

背景应安静、浅色、低噪，适合长时间扫读。不要使用强烈渐变或重装饰背景。首页应像工作收件箱，不像营销页。

### 卡片表面

卡片表面应清楚分组，但不要过厚。Needs Attention 可以有更明显边框或浅色提示面，In Progress 使用稳定的轻强调，Completed 更克制。

### 主操作

主操作应稳定、可信、不过度兴奋。适合用于 Review、Continue、Accept、Create Task。

### 关注状态

Needs Attention 应醒目但不焦虑。可使用温和的暖色或清晰的重点边框，而不是高饱和警告色。表达"需要你处理"，不是"系统出事了"。

### 进行中状态

In Progress 应让用户感觉任务正在稳定推进。适合使用冷静的蓝/绿系动势或细微活动反馈，但不要像系统监控报警。

### 已完成状态

Completed 应清晰但不抢注意力。它应该告诉用户"可以验收/回顾"，不应该和 Needs Attention 争夺视觉优先级。

### 危险状态

Stop、Fail、Delete 等危险动作应明确但克制。危险色只用于真正不可逆或中断性动作。

### 调试状态

Debug 应低优先级。适合灰色、单色、折叠区、辅助文案。它应该存在，但不应成为第一视觉层级。

## 5. 排版与信息密度

移动端要快速扫读。每张任务卡片不应该像日志摘录，也不应该像聊天消息。

任务卡片信息层级建议：

1. 任务标题
2. 人类可读状态
3. 最新有用进展
4. 下一步动作
5. 次级元数据

标题应短而明确。状态应是人类可读的短句。最新进展应限制在 1-2 行。下一步动作应可以一眼看到。次级 metadata 可以包括时间、更新时间、所属项目，但 host / CLI / tmux / logs 不应该出现在主层级。

信息密度建议：

- Needs Attention 卡片允许更高密度，因为用户要做决定。
- In Progress 卡片保持轻量，重点展示最新进展和是否需要动作。
- Completed 卡片最克制，重点展示可验收结果。
- Debug 信息进入折叠区，不参与主页面密度竞争。

## 6. 组件风格方向

### 任务卡片

任务卡片应像工作项，而不是聊天气泡。它需要明确标题、状态、最新进展和下一步。边界清晰、布局紧凑、可扫读。

### 需要关注卡片

Needs Attention 卡片是最高优先级。视觉上应有轻强调：更醒目的状态行、明确的 CTA、可读的原因说明。语气应是"需要你决定"，不是"错误报警"。

### 进行中卡片

In Progress 卡片应表达稳定推进。可以有小型状态动势、更新时间或最近事件，但不要显示原始日志。重点是"正在做什么"和"当前不需要你"。

### 已完成卡片

Completed 卡片应安静。它应该突出结果可查看、可验收、可继续，而不是抢占注意力。

### 下一步动作卡片

Next Action 是任务详情里的关键模块。它应比日志更靠前，比普通时间线更醒目。动作按钮应明确区分 Review、Continue、Accept、Pause、Stop。

### 活动时间线

时间线应叙事化，不是日志化。每条事件回答"工作发生了什么"，而不是贴运行时输出。时间线可以保留少量时间戳，但不应像终端滚动记录。

### 追加上下文输入

Add Context 应像任务上下文输入，不像聊天框。它应明确显示目标任务，支持 Hold to Talk 和 Type。输入文案应偏"为此任务添加上下文"，避免"随便问"。

### 调试/高级面板

Debug / Advanced 应折叠、低对比、专业。展开后可以显示主机、SSH、tmux、原始日志、重连、清理会话，但默认不争夺注意力。

### 空态

空态应解释产品循环：创建任务，让它运行，当它需要你时回来。不要先展示复杂配置表单。配置提示应作为发送前的必要步骤，而不是首屏主任务。

### 主行动按钮

Primary CTA 应服务于任务推进：创建任务、Review、Continue、Accept Result。不要让麦克风成为唯一或最大主按钮。

## 7. 动效与反馈

动效服务于“工作正在推进”的感知，而不是炫技。

### 任务状态切换

状态变化应有轻微过渡，让用户感到任务从 Running 到 Needs Attention / Completed 是可追踪的。避免强烈跳动或报警式闪烁。

### 任务卡片更新

任务卡片收到新进展时，可以有短暂高亮或轻微插入反馈。重点是告诉用户"这张卡更新了"，不是制造兴奋感。

### 语音录制反馈

语音录制反馈应明确但克制：录制中、整理中、已追加到某任务。必须显示目标任务，避免用户误以为在和通用助手说话。

### 新进展事件

新进展进入时间线时，可以用轻微淡入或短暂标记。不要像日志流一样持续滚动吸引注意力。

### 需要关注通知

Needs Attention 可以有更明确的视觉变化，但不要焦虑化。它应表达"轮到你了"，不是"出错了"。

### 完成状态

完成状态可以有非常轻的确认反馈。完成后视觉应快速回到安静状态，让它从注意力中心退到 Recently Completed。

## 8. 文案语调

UI 文案应避免：

- 技术术语
- Shell 风格措辞
- 原始运行时状态
- 过度 AI 热词

倾向：

- 人类可读
- 动作导向
- 冷静
- 简洁

示例：

不要：

```text
Runtime lost
```

建议：

```text
连接已暂停，需要时可重连。
```

不要：

```text
turnIdle
```

建议：

```text
等待你的下一步指令。
```

不要：

```text
Agent command
```

建议：

```text
执行方式
```

更多建议：

- `Observer detached` → `更新已暂停，重连以继续查看。`
- `Cleanup session` → `清理远端运行`
- `Raw log` → `调试日志`
- `Need approval` → `需要你的决定`
- `Mark completed` → `接受结果`

## 9. 不应做的事

Phase 2.5 UI 不该做：

- 不要把大麦克风继续作为首页视觉中心。
- 不要让聊天框成为唯一主入口。
- 不要把 tmux / SSH / host 放在主卡片上。
- 不要做成飞书/Slack 风。
- 不要做成终端控制台。
- 不要做成过重 Dashboard。
- 不要过早设计完整 Design System。
- 不要为了好看牺牲任务状态可读性。
- 不要把 Needs Attention 做成错误报警。
- 不要让 Debug 信息和用户决策同级。
- 不要让用户感觉自己必须持续盯着 Agent。

## 10. 下一步建议

Phase 2.5 UI 下一步应该先做：

1. 首页任务收件箱低保真原型
2. 任务卡片变体
3. 任务详情摘要/决策界面
4. 追加上下文入口
5. 高级调试折叠面板

不要直接进入全量 UI 重构。

推荐顺序：

- 先验证首页是否能让用户第一眼理解任务收件箱。
- 再验证任务卡片是否能表达状态、最新进展和下一步。
- 然后调整任务详情的首屏信息层级。
- 最后再整理追加上下文和调试的入口层级。

视觉方向应保持轻量：先把信息结构和状态语言做对，再决定更完整的视觉系统。
